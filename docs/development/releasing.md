# 提交、版本与发布规则

Agent 在提交、推送、打 tag 或发布前读取本文件；入口为根目录 AGENTS.md。
用户说“提交到 GitHub”时默认准备并发布一个经过测试的稳定版本；如果用户明确只推送
开发分支，则不发布、不要求每个中间提交升版。规则不替代用户对发布的授权。

## 版本及兼容政策

唯一版本来源是 `src/steertrace/__init__.py` 的 `__version__`，包配置及 HTML 生成器动态读取。
新报告页脚显示“生成工具：SteerTrace vX.Y.Z”，HTML 的 `generator` 元信息记录相同版本。
Agent 更新版本时须重新生成示例报告，核对页脚、元信息与 CLI 版本一致；不在模板中手工维护
第二份版本号。旧报告保留生成时的版本，升级工具不修改历史 HTML；重生成报告才使用新版本。
修复、文案及样式使用 PATCH；兼容功能增加使用 MINOR；1.0 后破坏兼容使用 MAJOR。
0.x 阶段不兼容变更至少升 MINOR，并在更新日志说明迁移；不能用 PATCH 隐藏破坏性变化。
CLI 参数、事件 schema、已安装 Skill 与配套代码的匹配属于兼容范围。

准备版本：

```bash
python3 scripts/release.py --bump patch --reason "修复说明；旧版仍受支持，不强制升级。"
```

`--minimum-supported X.Y.Z` 仅在旧版有重要正确性、安全或兼容问题时提高。
`release-policy.json` 必须描述升级原因及为何强制/不强制。最低版本不得降低。
没有达到最低版本的安装必须升级后才开展新分析；旧报告不重写、不删除。
新功能不自动构成强制升级理由。Agent 按改动判断版本，不机械地每次加 PATCH。
如果当前开发改动已准备了相应版本且尚未发布，更新同一版本的日志，不重复升版。

## 发布流程

1. 核对改动范围、私密材料排除、版本、CHANGELOG 和升级政策。
2. 执行 `python3 scripts/release.py --check`、完整单元测试及 `scripts/demo.py`，
   在隔离环境执行 `scripts/check_install.py`，核对生成 HTML 的页脚及 generator 版本与 CLI 一致。不声称结构测试证明语义分析正确。
3. 提交并推送开发分支；通过项目正常合并流程进入默认分支。不要绕过分支保护或强推；只有用户明确要求合并时才执行合并。
4. 默认分支 push 自动运行测试及 macOS/Windows 安装检查；成功后发布 job 检查远端版本与
   最低支持版本，自动创建并推送 `vX.Y.Z` tag，在同一个 job 构建并发布正式 Release。
   不需要手动创建 Release 或额外 PAT；使用该 job 的 `GITHUB_TOKEN`，写权限仅限发布 job。
5. tag push 及默认分支的手动 workflow_dispatch 也可重试。全局发布锁避免并发；同一版本和
   同一提交已发布则跳过，版本相同而提交不同则失败并要求准备新版本。禁止移动已有 tag、
   覆盖 Release 附件或把旧版本替换为最新版。断网和非首次发布的缺附件错误不能当作首次发布。
6. 发布附件包括源代码 ZIP 和 `steertrace-update.json`，包含版本、最低支持版本、原因、
   源提交及 ZIP 的 SHA-256。核实 Release、两个附件和版本检查结果后，再报告发布成功。

CI 调用 `scripts/publish_release.py`。GitHub 内置 token 推送 tag 不会再触发新的 push
工作流，因此创建 tag、构建和发布在同一 job 内完成，不依赖另一个 tag 工作流接力。
用户要求合并并发布时，Agent 应跟进远端 CI 至成功、失败或需要用户处理，不能将推送完成
称为正式发布完成。版本已经准备且尚未发布时沿用该版本，不为合并动作重复升版。

`python3 scripts/release.py --build <新目录>` 只从干净、已提交且有匹配 tag 的源码构建，
不会提交、推送或发布。输出目录应在仓库外或忽略目录中。tag 发布失败时先核对远端结果，
不要覆盖已有 Release 的附件。GitHub 未提供发布凭据或仓库权限时说明具体阻碍。

## 安装端行为

每次 Skill 调用先执行管理安装的 `update`，默认自动处理受支持的稳定更新。
只查询固定官方 GitHub 仓库的公开发布信息，不上传会话、路径、报告或密钥。
查询缓存 24 小时，显式更新用 `--force-check`。更新策略以 GitHub 最新正式 Release
附件为准，不读取开发分支上的任意说明来执行命令。

升级下载固定版本附件，校验摘要，独立建环境，验证 CLI、安装包报告链路及源代码示例，
成功后才替换 Skill 并写安装记录。失败保留原安装；受支持版本可继续，低于已知最低
支持版本则暂停。离线时允许受支持安装继续，明确无法确认最新；已知强制要求不会因离线消失。
不能联网且没有管理安装时不声称安装成功。

本地源码或 Skill 有修改时停止自动覆盖；链接安装、无来源副本和旧版需显式迁移。
旧 Skill 不会自动获得检查能力，用户必须先完成一次升级。
