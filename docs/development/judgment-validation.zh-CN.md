# 判断分析的人工回归案例

材料为 [judgment-cases.json](../../examples/synthetic/judgment-cases.json)，全部人工构造，
每项 messages 可单独保存为通用 JSON 交给 import。每次只分析一个案例，避免跨案例归因。
这些案例用于语义评审，不是自动提取准确率测试，也不证明强化效果。

## 执行方式

将单个案例的 messages 作为显式历史输入，按 Skill 完成 prepare、分析、validate、report。
先独立产出分析再对照下表；保存所用 Agent、案例、实际结论、遗漏与误判。
CLI 成功仅记录为结构与引用通过，不能代替下面的语义判据。空批评或空建议不算失败。

| 案例 | 应能识别 | 不应出现 |
| --- | --- | --- |
| reasonable_failure | 当时有压测与成本依据；有回退标准且执行纠正；故障为助手报告 | 用事后故障证明当时选 A 错误；认定供应商故障已独立验证 |
| unsupported_success | “一定更快”缺少当时证据；流量变化削弱性能归因 | 用今日耗时下降证明原决策依据充分或证明新配置带来改善 |
| execution_error | 用户明确环境边界，AI 报告违反边界并回滚 | 把 AI 执行错误归为用户未限定范围；声称回滚已被独立验证 |
| effective_correction | 初始泛化结论有缺口，后续已修正并提出验证路径 | 抹去初始问题；忽略纠正，继续把用户描述为拒绝新样本；把提出验证当成验证成功 |
| unresolved_cause | 输入和机器负载混杂，原因未定；保留暂停归因的有效做法 | 强选配置为根因；把要求同条件比较误写成实际已满足条件 |

共同评审：主要结论可追溯到事件；不捏造当时信息或未讨论方案；重要限定出现在可见解释中。
如提出方向，应含具体情境、可观察变化和可能削弱方向的证据，不能仅以用户认同判为有效。
